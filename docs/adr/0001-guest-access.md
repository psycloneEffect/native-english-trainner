# ADR 0001: ゲスト利用（ポートフォリオ向けデモ）

- 状態: 提案
- 日付: 2026-11-02
- 対象読者: このリポジトリの開発者・運用者
- 前提: v0.8.1 時点の構成（共有アカウント＋管理者、KVによる日次上限、署名付きCookie）

## 1. 背景

ポートフォリオとして、登録なしで触れる公開デモが欲しい。
一方で、このアプリは1回の生成ごとに Claude API（web_search 含む）を呼ぶため、
不特定多数に開くと費用が直接増える。現行の所内向け構成は「共有アカウントを知っている人だけ」
という前提で上限を緩めにしている。

当初案は「ゲストアカウント、登録不要、IP単位で5回、UTC 0時リセット」。
本ADRはこれを具体化し、所内向けインスタンスを危険にさらさない形に整理する。

## 2. 決定（要約）

1. **デモは所内向けと別のWorkerとしてデプロイする。** 同じリポジトリ・同じコードを、
   wrangler の環境 `demo` で別名デプロイする。KV・Secret・APIキー・費用上限をすべて分ける。
2. **費用の最終防衛は Claude Console のワークスペース単位の上限。** デモ専用ワークスペースと、
   そのワークスペースに限定したAPIキーを使う。
3. **ゲストはまず「生成済みサンプル」を見る。** 自由入力の生成は、IP単位5回／日＋全体上限の範囲で許可する。
4. **ボット対策に Turnstile を必須にする。** 生成1回ごとにトークンを検証する。
5. **IPの識別子は日替わりソルト付きHMACにする。** 現行の無塩SHA-256を置き換える（所内向けにも適用）。
6. 日付境界は設定可能にし、既定は日本時間（`Asia/Tokyo`）。画面には閲覧者の現地時刻でリセット時刻を出す。

## 3. 構成

### 3.1 デプロイの分離

| 項目 | 所内向け（現行） | デモ |
|---|---|---|
| Worker名 | `native-english-trainner` | `native-english-trainner-demo` |
| URL | `native-english-trainner.ai-builds-lab.workers.dev` | `native-english-trainner-demo.ai-builds-lab.workers.dev`（仮） |
| デプロイ | `npx wrangler deploy` | `npx wrangler deploy --env demo` |
| ログイン | 共有アカウント／管理者 | ゲスト／管理者（共有アカウントは無効） |
| KV | 現行の `QUOTA` | デモ専用の Namespace |
| Claude APIキー | 所内用ワークスペースのキー | デモ用ワークスペースのキー |

- wrangler の環境では `vars` と `kv_namespaces` が継承されないため、`env.demo` に明示的に全部書く。
- Workers Builds は同じリポジトリに複数のWorkerを接続でき、Worker ごとにデプロイコマンドを設定できる。
  デモ用に2つ目の接続を作り、デプロイコマンドを `npx wrangler deploy --env demo` にする。
- Secret はWorkerごとに登録する。所内向けの値を流用しない（1用途1キー）。

分ける理由: 同じWorkerにゲストを足すと、ゲストの濫用が所内利用者の全体枠
（`DAILY_LIMIT`）と同じAPIキーの費用上限を食う。障害やキー失効の影響範囲も混ざる。

### 3.2 費用上限（Claude Console）

- **Default Workspace にはワークスペース単位の費用上限を設定できない。** 組織全体の上限だけが掛かる。
- そのため、所内用とデモ用にワークスペースを作り、それぞれに限定したAPIキーを発行し、
  ワークスペースごとに月額上限を設定する。デモ側は低め（例: 月5ドル）に置く。
- 現行のキーが Default Workspace のものなら、所内用ワークスペースのキーに差し替える
  （新キー発行 → Secret 差し替え → 動作確認 → 旧キー失効）。

アプリ側の回数制限は「桁違いの使われ方を止める」ためのもので、KVの結果整合により数回の超過はありうる。
金額の上限はConsole側が担う。

### 3.3 wrangler.jsonc（追加分の例）

```jsonc
{
  // ...既存の設定（所内向け）...
  "vars": {
    "MODEL": "claude-sonnet-5",
    "DAILY_LIMIT": "30",
    "PER_CLIENT_LIMIT": "10",
    "ADMIN_DAILY_LIMIT": "100",
    "QUOTA_TZ": "Asia/Tokyo"
  },
  "env": {
    "demo": {
      // name は自動で native-english-trainner-demo になる
      "kv_namespaces": [{ "binding": "QUOTA", "id": "<デモ用のNamespace ID>" }],
      "vars": {
        "MODEL": "claude-sonnet-5",
        "GUEST_MODE": "on",
        "GUEST_DAILY_LIMIT": "30",
        "GUEST_PER_CLIENT_LIMIT": "5",
        "ADMIN_DAILY_LIMIT": "50",
        "QUOTA_TZ": "Asia/Tokyo",
        "TURNSTILE_SITE_KEY": "<サイトキー（公開値）>"
      }
      // Secret（ダッシュボードで登録・値はここに書かない）:
      //   ANTHROPIC_API_KEY  デモ用ワークスペースのキー
      //   SESSION_SECRET     所内向けと別の値
      //   QUOTA_SALT         IP識別子のHMAC鍵
      //   TURNSTILE_SECRET   Turnstile のシークレットキー
      //   ADMIN_USERNAME / ADMIN_PASSWORD（任意）
    }
  }
}
```

`assets` と `main` はトップレベルのものが環境にも適用される前提だが、実装時に
`wrangler deploy --env demo --dry-run` でバインディング（`ASSETS`, `QUOTA`）を確認する。

## 4. ゲストの利用体験

### 4.1 画面

1. トップに「ゲストとして試す」ボタン。下に小さく「管理者ログイン」。
2. ゲストで入ると、まず **生成済みサンプル3件** を表示する（静的ファイル。トークン消費なし・即時）。
3. 「自分の表現で試す」で通常の入力画面へ。ここからの生成がゲスト枠を消費する。
4. 入力画面の上部に常時表示:
   - 「入力内容は Claude（Anthropic）に送信されます。個人情報や社外秘の内容は入れないでください」
   - 残り回数とリセット時刻（例: 「本日の残り 3 回・11/3 0:00（日本時間）にリセット／あなたの時刻: 11/2 16:00」）
5. 上限到達時は理由別の文言を出し、サンプルへの導線を置く。
   - 端末上限: 「この端末の本日の上限（5回）に達しました」
   - 全体上限: 「デモ全体の本日の上限に達しました」
6. フッターにプライバシー表記（何を送るか、何を保存しないか）へのリンク。

### 4.2 サンプルとプリセット

- サンプル3件は `public/samples/` に Markdown とその元入力（JSON）を置く。管理者が生成して手で確定させる。
- 入力欄にプリセット（サンプルと同じ入力）を選べるようにする。サーバー側で正規化後の入力が
  サンプルと完全一致したら、APIを呼ばずにサンプルを返し、枠も消費しない。
  - 一致判定はサーバー側で行う。クライアントの「サンプルです」という申告は信じない。

### 4.3 ゲストセッション

- `POST /api/guest` で発行。署名付きCookie（既存の `sid`）に `r: "guest"` を入れる。有効期間は24時間。
- セッションは便宜上のものでしかない。Cookie を消せば何度でも取り直せるため、
  **上限はセッションではなく IP と全体で数える。**
- `GUEST_MODE` が `on` でないWorkerでは `/api/guest` は 404。

## 5. 上限

### 5.1 数え方

| スコープ | キー | 既定 | 目的 |
|---|---|---|---|
| ゲスト・端末ごと | `gen:<日付>:g:<clientId>` | 5 | 1人が枠を使い切るのを防ぐ |
| ゲスト・全体 | `gen:<日付>:guest` | 30（費用実測後に確定） | 財布を守る |
| 管理者 | `gen:<日付>:admin` | デモでは 50 | 管理者パスワード漏洩時の被害を限定 |

- デモでは管理者も無制限にしない。漏洩時に上限が一切効かなくなるため。
- カウントは Claude API を呼ぶ前に加算する（現行と同じ。失敗でもトークンは消費されるため）。
- KVが無ければ生成しない（現行と同じ fail-closed）。

### 5.2 検査の順序（`POST /api/generate`、ゲスト）

1. セッションの役割が `guest`
2. 入力の正規化と検証（ゲストは `MAX_INPUT_LEN` を短くする。例: 200文字）
3. プリセット一致ならサンプルを返して終了（以降の検査・消費なし）
4. Turnstile トークンの検証（siteverify）
5. 全体上限
6. 端末上限
7. 両カウンタを加算 → Claude API 呼び出し

Turnstile を上限より先に置くのは、ボットのリクエストでKVの読み書きをさせないため。

### 5.3 端末の識別子

- IPv4 はアドレスそのもの、IPv6 は先頭 /64 を単位にする。IPv6 は1契約に /64 以上が
  割り当てられることが多く、アドレス単位だと実質無制限になるため。
- 識別子 = `HMAC-SHA256(日替わり鍵, 正規化したIP)` の先頭16桁（16進）。
  日替わり鍵 = `HMAC-SHA256(QUOTA_SALT, 日付)`。
  - 無塩SHA-256だと IPv4 全空間（約43億）を総当たりして元のIPに戻せる。鍵付きにすれば
    KVの中身が漏れても戻せない。
  - 日替わりにすることで、日をまたいだ同一人物の追跡もできなくなる。
- 所内向けにも同じ方式を適用する。切り替え当日は端末カウンタが一度リセットされる（全体カウンタは維持）。

### 5.4 リセット時刻

- `QUOTA_TZ`（IANAタイムゾーン名）で日付境界を決める。既定 `Asia/Tokyo`。
- 当初案のUTC 0時は、日本では朝9時に切り替わり、利用者の感覚とずれる。
  主な閲覧者が日本の採用担当者と想定されるため、日本時間を既定にする。
- 画面には、サーバーの基準時刻と、ブラウザの現地時刻の両方を出す（海外から見た場合の混乱を避ける）。
- 実装上は `resetAtJst()` を `QUOTA_TZ` 対応の `resetAt(tz)` に一般化する。

## 6. Turnstile

- ウィジェットは Invisible（または Managed）。生成ボタン押下時にトークンを取得し、
  `POST /api/generate` の本文 `turnstileToken` で送る。
- Worker は `https://challenges.cloudflare.com/turnstile/v0/siteverify` に
  `secret`（`TURNSTILE_SECRET`）、`response`、`remoteip`（`cf-connecting-ip`）を送って検証する。
  **siteverify の検証は省略できない。** クライアント側のウィジェットだけでは防御にならない。
- トークンは300秒で失効し、1回しか使えない。生成ごとに取り直す。
- 検証失敗は 403 `turnstile_failed`。siteverify 自体に到達できない場合も失敗として扱う（fail-closed）。
- 所内向けインスタンスでは使わない（ログイン必須のため）。

| `worker/input.js` | 役割に応じた最大長 |
| `public/app.js` | ゲスト入口、サンプル表示、Turnstile、注意書き、現地時刻表示 |
| `public/samples/` | 新規。サンプル3件 |

新しいエラーコード:

| コード | HTTP | 意味 |
|---|---|---|
| `guest_disabled` | 404 | このWorkerではゲストが無効 |
| `turnstile_failed` | 403 | ボット判定の失敗・トークン失効 |
| `quota_exceeded`（`scope: "guest"` / `"client"`） | 429 | ゲスト全体／端末の上限 |

バージョン: 機能追加のため **0.9.0**（MINOR）。IP識別子の変更も同じリリースに含める。

## 8. テスト観点

- ゲストセッションの発行・`GUEST_MODE` off での 404・共有アカウントがデモで無効であること
- プリセット一致で API を呼ばず、カウンタも増えないこと（正規化の差: 前後空白・全角半角）
- Turnstile: トークン無し／不正／再利用／siteverify 到達不能 → いずれも 403
- 上限: 端末5回目まで成功・6回目で 429 `client`、全体上限で 429 `guest`
- IPv6 の同一 /64 内の別アドレスが同じ端末として数えられること
- 日付境界: `QUOTA_TZ` の0時前後でキーが切り替わること
- 所内向けインスタンスの挙動が変わらないこと（ゲストのルートが出ない、識別子変更以外の差がない）
- `wrangler deploy --env demo --dry-run` でバインディングを確認

## 9. 検討した代替案

| 案 | 不採用の理由 |
|---|---|
| 所内向けWorkerにゲストを追加 | 全体枠・APIキー・費用上限が共有され、ゲストの濫用が所内利用を止める |
| セッション（Cookie）単位で5回 | Cookie を消せば無限に取り直せる |
| ゲストもアカウント登録制 | 「登録なしで触れる」というデモの目的に反する。アカウント管理は別のロードマップで扱う |
| Durable Object で厳密に数える | 現段階では過剰。KVの数回の超過は Console の上限で吸収できる。濫用が観測されたら再検討 |
| サンプルのみ（生成不可）のデモ | 費用はゼロだが、Webアプリとしての動作を見せられない。サンプルは入口として併用する |
| Cloudflare の Rate Limiting バインディング | 分・秒単位の連打対策には向くが、日次の回数管理には向かない。連打対策が必要になったら併用を検討 |

## 10. 未決事項

1. **リセットの基準**: 日本時間（推奨）か、当初案のUTCか。
2. **ゲスト全体の日次上限**: 1回あたりの費用を実測して決める（目安: 月額上限 ÷ 30日 ÷ 1回の費用）。
3. **サンプル3件の題材**: 何を見せるか。
4. **デモの名前とURL**: `native-english-trainner-demo` でよいか。リポジトリ名の綴り（trainner）を公開URLにも残すか。
5. **プロンプト内のペルソナ名「Taka」**: 公開前に残すか外すか。
6. **デモでの管理者ログイン**: 置くか（置く場合は上限付き）、所内向けだけにするか。
